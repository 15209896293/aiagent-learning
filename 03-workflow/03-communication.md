# 3.3 Agent 的"沟通技巧"

## 这是一个协作关系，不是魔法

你和一个真人程序员怎么协作：
- 交代需求 → 对方理解 → 动手 → 给你看结果 → 你提修改意见 → 改

和 Agent 协作完全一样。区别是 Agent 不会主动说"我没听懂"——你得更主动地判断它的状态。

---

## 什么时候该中断 Agent

### 信号 1：Agent 跑偏了

```
你：帮我给按钮加个 loading 状态
Agent：好的，我先分析整个项目的状态管理方案，
      然后考虑是否引入 Redux...
      ← 跑偏了，你只要加个 loading
```

**立即中断。** 它在浪费你的 token 和时间。正确回复：
> "停。不用分析架构，就在 Button.vue 第 30 行加个 :loading 属性。"

### 信号 2：Agent 开始"编造"

```
你：读一下 src/config.ts
Agent：这个文件里定义了 API_URL = 'https://api.example.com'
      ← 实际上它没读文件，在猜
```

**立即中断。** 确认它有没有真的读文件：
> "你真的读了那个文件吗？用 Read 工具读一下再告诉我。"

### 信号 3：Agent 在循环

```
Agent：让我试试这个方案...
      ← 写了代码
Agent：不对，这个方案有问题，让我换个方式...
      ← 删了重写
Agent：还是第一个方案好，让我改回去...
      ← 循环了
```

**立即中断。** 它在消耗大量 token 反复横跳。正确做法：
> "停。你想清楚方案再动手。先告诉我你打算怎么做，我确认了你再写。"

### 信号 4：Agent 出结果了，但你不确定对不对

**不要继续。** 先验证：
> "把这个结果跑一下，看能不能运行。" 或 "解释一下你为什么这么写。"

---

## 什么时候让 Agent 继续

### 信号 1：Agent 在执行一连串相关操作

```
Agent：我先搜索所有用到 User 的文件...
      找到了 5 个。现在一个个读...
      读了 user.py，现在读 auth.py...
```

**让它继续。** 它在做依赖链操作，打断会丢失上下文。

### 信号 2：Agent 的输出看起来靠谱，但你知道还要优化

```
Agent：（写了能跑的代码，但边界情况没处理）
```

**不要打断重来。** 在它的基础上追加：
> "代码可以跑，干得好。现在加上空值处理和超时重试。"

### 信号 3：Agent 在思考/规划阶段

```
Agent：这个需求可以有两种方案：
      方案 A：...
      方案 B：...
      我建议方案 A，因为...
```

**让它继续。** 它在做有价值的分析。分析完你再判断。

## 给 Agent 反馈让它修正 vs 自己动手改

### 让 Agent 修正
```
适合：逻辑复杂、改动点多、你懒得自己打字的场景
代价：可能需要 1-2 轮来回
做法："第 45 行的 timeout 改成 5000，第 78 行的错误消息改成英文"
```

### 自己动手改
```
适合：改一个变量名、改一个数字、删一行 console.log
      → 你手动改 3 秒，让 Agent 改要 30 秒 + 1000 token
做法：自己动手，不告诉 Agent
```

### 判断标准
```
改动量 < 5 行 + 不需要思考 → 自己改
改动量 > 5 行 or 需要逻辑判断 → 让 Agent 改
```

## 多轮对话的策略

### 一个任务 = 一个会话

这是最重要的规则。为什么：

```
会话 A：做登录功能（15 轮）
会话 B：做搜索功能（20 轮）
会话 C：做用户设置（10 轮）

vs

一个会话做全部 3 个功能（45 轮）
  → 第 45 轮时上下文已经 10 万 tokens
  → 上下文污染严重
  → Token 费用是 3 个独立会话的 3-5 倍
```

### 会话拆分信号

当出现以下任一信号，立即开新会话：
1. 对话超过 20 轮
2. Agent 开始"忘记"你之前说的
3. 感觉比刚开始慢了
4. 完成了当前独立功能

### 新会话如何延续

```
你（新会话）：上个会话我们完成了登录功能，
             代码在 src/api/auth.py。
             现在我要做搜索功能，先读一下项目结构。
```

不需要重述一切，只需要告诉 Agent 从哪开始。
