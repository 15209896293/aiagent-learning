# 4.1 Token 燃烧的 7 种死法

每一个踩过坑的人都经历过。提前知道，省下的钱比你想象的要多。

---

## 死法 1：无限循环调用工具

### 场景
Agent 调用工具 → 工具返回错误 → Agent 用同样的参数再调一次 → 又失败 → 再调...

```
Agent：read_file("src/component/login.tsx")
宿主：File not found
Agent：read_file("src/component/login.tsx")   ← 再来一次？
宿主：File not found
Agent：read_file("src/component/login.tsx")   ← 还来？
```

### 原因
Agent 没有"失败"反馈回路。它不知道这个错误意味着"文件不存在"还是"工具暂时不可用"。

### 止损
- 看到 Agent 连续 3 次调用同一个工具且都失败 → **立即中断**
- 手动告诉它文件路径或换方式
- 在 prompt 里预设："如果文件不存在，不要重试，直接告诉我"

## 死法 2：上下文无限膨胀

### 场景
一个会话持续用，Agent 每轮都要把全部历史塞进请求里。

```
第 1 轮：上下文 2000 tokens，¥0.006
第 10 轮：上下文 50,000 tokens，¥0.15
第 20 轮：上下文 150,000 tokens，¥0.45
第 30 轮：上下文 300,000 tokens，¥0.90
...
一次 30 轮会话的后 20 轮，每轮都在烧前 20 轮全量的钱。
```

### 每一轮的实际成本

| 轮次 | 估计上下文 | 本轮费用（DeepSeek-V3） |
|------|-----------|------------------------|
| 1 | 2K | ¥0.006 |
| 5 | 20K | ¥0.06 |
| 10 | 50K | ¥0.15 |
| 20 | 150K | ¥0.45 |
| 30 | 300K | ¥0.90 |
| **合计** | - | **~¥7.00** |

同样 30 轮，拆成 3 个会话（每会话 10 轮）= **~¥1.50**。省 78%。

### 止损
- 10 轮以上开始考虑开新会话（这个会话快到了）
- 看到 `/compact` 提示就压缩
- 完成一个独立功能 → 立即开新

## 死法 3：重复读取大文件

### 场景
Agent 每次修改都重新读整个文件确认。

```
修改 A 函数 → read_file("bigfile.tsx")  ← 2000 行
修改 B 函数 → read_file("bigfile.tsx")  ← 又 2000 行
修改 C 函数 → read_file("bigfile.tsx")  ← 总共读了 6000 行
```

### 为什么浪费
Edit 工具已经确认修改成功。不需要再读回来验证。工具返回的错误信息比重新读文件更准确。

### 止损
- 信任工具返回结果，不要"再读一遍确认"
- 一次修改多个改动尽量合并成一个 Edit
- 如果你自己已经知道文件内容，不要让 Agent 重复读

---

## 死法 4：无效重试叠加

### 场景
网络超时 → API 自动重试 → 但重试时整个请求（包括上下文）重发 → 第一次请求已经扣费了，第二次又扣。

```
你：帮我分析这个文件（文件 3000 行 → ~8000 tokens）
→ API 超时
→ 自动重试：又发送 8000 tokens
→ 你被扣了 16000 tokens 的钱，但 Agent 只回复了一次
```

### 止损
- **看到 "Retrying..." → 立即 Ctrl+C**
- 检查网络后再发
- 大文件分析尽量拆成小文件分别问

---

## 死法 5：长会话累积（你正在经历）

### 场景
一次会话从早上用到晚上，一直在加新任务。

```
上午：做登录功能（上下文开始积累）
下午：做搜索功能（上午的登录对话还在上下文里）
晚上：做设置页面（上下文里有登录 + 搜索的全部历史）
→ 晚上每条消息的成本是早上的 100 倍
```

### 为什么这么危险
- **你看不到上下文大小**，感觉"一切正常"
- 实际每轮都在给所有历史买单
- 当 Agent 开始变慢或"失忆"时，已经烧了很多钱

### 止损
- **30 轮硬上限**：一到就开新会话，不要犹豫
- 每隔 5 轮粗略评估一下：这次请求大概多少 token？
- "一天一个会话" = 一天烧上百块钱（你没感觉）

## 死法 6：错误的 Tool Schema 导致反复纠错

### 场景
你定义了一个工具，但参数描述不够清楚。Agent 反复试不同的参数组合。

```
你写的 Schema：{"file_path": "要操作的文件"}
Agent 输出：{"file_path": "login.tsx"}  ← 相对路径
宿主：文件找不到
Agent：{"file_path": "./login.tsx"}  ← 加了 ./
宿主：文件找不到
Agent：{"file_path": "/login.tsx"}  ← 加了 /
宿主：文件找不到
→ 3 次调用全部失败，都在烧 token
```

### 止损
- Schema 里明确写："file_path: 文件的绝对路径，例如 /home/user/project/src/login.tsx"
- 描述里加例子，模型通过例子学习
- 如果 Agent 连续出错，在 schema 里加更详细的约束

---

## 死法 7：模型降级 Fallback 疯狂消耗

### 场景
你配了 Opus 作为主模型，但 API 偶尔报错 → 自动 fallback 到 Sonnet → Sonnet 又出错 → 错误重试机制触发 → 两个模型都在烧钱。

### 为什么危险
- Fallback 通常不通知你，你看不到
- Sonnet 虽然便宜，但出错重试会让总成本超过直接成功的 Opus
- 如果不加 fallback 限制，可能一直降级到最差的模型还失败

### 止损
- 关闭自动 fallback，或限制降级次数（最多 1 次）
- 主模型失败了就停，手动检查问题
- 不要"自动换模型试试"——换模型 ≠ 换结果
