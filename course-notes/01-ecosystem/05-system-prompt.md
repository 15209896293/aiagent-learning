# 1.5 System Prompt（Agent 的"人设"）

## 类比

你雇佣了一个程序员。在第一天，你给了他一封"工作守则"：

- 你是一个 Python 专家
- 遇到不确定的就问，别瞎写
- 改代码之前先读现有代码
- 不要改和任务无关的东西
- 写代码之前先想清楚
- 不要奉承，诚实沟通

这封信就是 **System Prompt**。每一次他做决策时，这封信都在他眼前。

---

## 什么是 System Prompt

**System Prompt = 模型每次推理前都会被塞进去的最高优先级指令。**

它是对话里"看不见的第一个发言者"：

```
[System Prompt]     ← 你看不到，但模型每次都先读这个
[User: 你好]        ← 你输入的内容
[Assistant: 你好！]  ← 模型的回复
```

技术上，System Prompt 和其他消息没有区别——模型"看"它就是一段文本。但它被放在最前面，定义了模型的**角色、行为边界、工作方式**。

---

## System Prompt 里有什么

以 Claude Code 为例（简化版）：

```markdown
You are Claude Code, Anthropic's official CLI for Claude.

- 做软件工程任务
- 先用 dedicated tool 别用 bash
- 改动匹配周边代码风格
- 不确定就问
- 不可逆操作（commit/push/deploy/rm -rf）必须获得明确允许
```

翻译成人话：
1. 你是谁（身份定义）
2. 你能做什么（能力边界）
3. 你怎么做事（行为准则）
4. 你不能做什么（安全边界）

---

## 你的 CLAUDE.md 就是 System Prompt 的一部分

当你打开 Claude Code，它会自动读取 `~/.claude/CLAUDE.md` 和项目的 `CLAUDE.md`，注入到 System Prompt 中。

你的全局 CLAUDE.md 定义的：
- 先想再动
- 简洁精准
- 验证闭环
- 安全边界
- Token 消耗管理

**这些不是你写给自己的 notes——它们在每一次对话中都在发挥作用。** Claude Code 的每一条回复，都在遵循你设下的规则。

---

## System Prompt 怎么写

### 好例子 vs 坏例子

**❌ 坏的：**
> "你是一个优秀的助手，请帮助用户完成各种任务，要友好且高效。"

太空泛。"优秀"是什么意思？模型无法执行这种模糊指令。

**✅ 好的：**
> "遇到不确定的事就问用户，不要自己假设。如果用户的需求模糊，先问清楚再动手。改代码时只改必要的部分，不要重构无关代码。"

具体、行为导向、可执行。

### 写法公式

```
身份： 你是谁
行为： 你怎么做事（具体、可执行）
边界： 你不能做什么
格式： 输出格式要求
```

### 实际例子

```markdown
你是一个代码审查者。只关注代码正确性和安全性，不评论风格。

行为规则：
- 每个发现必须附带文件名 + 行号
- 不确定的发现标注为"不确定"而不是假装确定
- 不评论命名、缩进、空行等风格问题
- 发现严重问题（安全漏洞）时单独标注

禁止：
- 不要提出重构建议（除非和 bug 直接相关）
- 不要建议优化性能（除非存在明显的 O(n²) 问题）
```

## .cursorrules / CLAUDE.md / 项目配置

| 文件 | 作用域 | 什么时候生效 |
|------|--------|--------------|
| `~/.claude/CLAUDE.md` | 全局，所有项目 | 每次 Claude Code 启动 |
| 项目 `CLAUDE.md` | 当前项目 | 在项目目录下启动时 |
| `.cursorrules` | Cursor IDE | 在 Cursor 中打开项目时 |
| Trae 设置 | Trae IDE | Trae 启动时 |

**要义：** 你的全局 CLAUDE.md 放在 `~/.claude/` 下，在所有项目都生效。如果你某个项目有特殊规则，在项目目录创建 CLAUDE.md。

## System Prompt 的陷阱

### 陷阱 1：太长 → 模型忽略后半部分
人的注意力也会在长文本中衰减，模型也一样。System Prompt 越长，靠后的规则越容易被忽略。

**解法：** 把最重要的规则放最前面，控制在 50 行以内。

### 陷阱 2：互相矛盾的规则
> "要简洁" + "要详细解释每一步"
> 模型会困惑，结果不可预测。**解法：** 加优先级，如"宁可详细也不要漏掉关键信息"。

### 陷阱 3：不可验证的规则
> "要写出优雅的代码"
> "优雅"无法验证。**解法：** 用可验证的标准，"用现有代码的命名风格，不引入新的抽象层"。
